## 2. 已知问题清单（静态推断）

### 2.1 平台实现规模差距悬殊

抖音 upload.ts 仅 197 行，是快手 2710 行的 **7%**。小红书 286 行（10%）、视频号 258 行（9%）同样处于早期阶段。

推测各平台当前状态：
- **抖音**：基础上传流程已跑通，publish.ts 200行与 upload.ts 197行规模相近，但 S09 需大量补充风控处理
- **小红书**：upload.ts 286行中等规模，但 schedule.ts 仅 42行（最短），且 `serverScheduledPublish: false` 确认不支持定时发布
- **视频号**：upload.ts 258行中等，publish.ts 162行最短，选择器 122行（最长）可能包含更多平台细节

### 2.2 选择器可能不完整

| 平台 | selectors.ts 行数 | 推断 |
|------|-----------------|------|
| 抖音 | 57行 | 行数最少，与快手 106行差距明显，可能缺失次要操作的选择器 |
| 小红书 | 107行 | 与快手接近，较为完整 |
| 视频号 | 122行 | 最长，但 0 单元测试覆盖 |
| 快手 | 106行 | 基准实现，8个单元测试覆盖 |

### 2.3 测试覆盖严重不足

- **单元测试**：抖音 2 个，小红书 0 个，视频号 0 个，快手 8 个
- **E2E 测试**：仅 douyin.test.ts（210行）存在，其他 3 平台完全无 E2E

### 2.4 缺少基础设施组件（静态推断）

从代码结构推断，以下组件**尚未实现或仅部分实现**：

| 组件 | 预期位置 | 状态 |
|------|---------|------|
| base/PlatformError | platform/base/ | 大概率未实现 |
| TopicSanitizer | platform/base/ 或 ai/ | 大概率未实现 |
| DebugRecorder | platform/base/ | 大概率未实现 |
| Watchdog | core/ | 大概率未实现 |

### 2.5 状态机精度

`core/TaskScheduler.ts` 目前仅实现 4 态（pending → running → success/failed），S06 设计需要 8 态。目前状态机精度不足，重试策略和错误分类都会受影响。

## 6. 失败归因分类（按 S06 设计共 8 类）

基于代码静态推断 + Story 描述，各错误类型预期表现：

| # | 错误类型 | 预期表现（静态推断） |
|---|---------|-------------------|
| 1 | 选择器失效 | 抖音 selectors.ts 仅 57 行，DOM 变更时最可能失效 |
| 2 | 平台限流 | 抖音 hourly: 10/daily: 50，小红书 hourly: 5/daily: 20（最严格） |
| 3 | Cookie 过期 | 所有平台通病，需扫码重登录 |
| 4 | 网络超时 | upload.ts 行数少的平台（抖音 197行）错误处理可能不足 |
| 5 | 账号风控 | 小红书最可能（config.yaml 明确建议有头模式） |
| 6 | 视频格式不兼容 | 仅在 publish.ts 层面检查，upload.ts 行数少可能未覆盖 |
| 7 | 定时发布失效 | 小红书 `maxScheduleDays: 0`，定时功能完全不工作 |
| 8 | 未知错误 | 状态机仅 4 态，无法精细区分，归类为"未知"概率高 |
